# 多模型舰队与能力路由

统一入口现在会把 vLLM 与 llama.cpp 管理器中的主实例和并行实例聚合成一个“模型舰队”。它不会替代两个管理器的启动能力：模型仍在对应管理器中启动，统一入口负责观察、规划和把请求送到已经驻留显存的正确实例。

## 现在具备的能力

- `GET /api/fleet`：返回运行实例、模型能力、GPU 显存账本、规划空槽和路由设置。
- `POST /api/fleet/settings`：保存 `balanced`、`throughput` 或 `multimodal` 模式，以及 `maxUtilizationPct` 显存安全线和 `reserveMb` 固定预留。设置使用原子写入。平衡模式优先主实例，吞吐模式优先 vLLM，多模态模式会尽量把纯文本请求留给文本专用模型。
- `POST /api/fleet/route-preview`：只预演路由，不调用模型，适合在加载新模型前检查目标实例。
- `/gateway/auto/*`：聚合所有已经就绪的运行实例。显式模型名按驻留模型匹配；`auto`、`default` 等泛型名会按文本、视觉、音频、Embedding、Rerank 或工具调用能力选择。未知的非泛型模型名直接返回 404，不会静默回落到另一个模型。容器标签中的 `lastKnown` 模型只用于展示加载状态，不会提前进入目录或接收流量。
- OpenAI/OpenCode 泛型请求只改写请求体中的 `model` 字段，提示词和响应正文不会写入访问日志。
- 统一入口会为目标实例附加短期签名；OpenAI、Claude 与 OpenCode 到管理器后仍锁定同一实例，目标消失时返回 503，不会改投其它副本。
- 服务 API Key 会同时约束所属管理器和允许模型；vLLM 的 Key 不会看到或误路由到 llama.cpp，模型短别名也只从该客户端有权看到的模型生成。

## 显存账本的含义

页面中的显存条是调度规划视图，不是 CUDA 的硬预留。两个管理器报告同一张物理 GPU 时，统一入口会去重并采用同卡读数的最大值，避免把总显存和已用显存重复相加；“安全线”和“固定预留”都可在统一入口主动设置。首次启动或配置文件不存在时才使用 85% 与 8 GiB 作为兜底默认值。

模型启动另有主机级硬准入：vLLM 与 llama.cpp 通过 `D:\AI\.runtime\gpu-admission` 下的跨进程原子租约锁定每张 GPU 的预算。新增并行实例会先准入；替换现有实例时，会在同一把全局锁内创建可回滚容器快照、释放旧实例显存、重新读取遥测并写入新租约。准入失败会在释放全局锁前恢复旧实例，避免短暂空档被另一个管理器抢占。锁内预算为：

`min(实时空闲 - 用户设置的固定预留 - pending，GPU 总量 × 用户设置的安全线 - 实时已用 - pending - 启动余量)`

统一入口把策略持久化到 `service-entry/data/fleet-settings.json`。两个管理器会在每一次新模型准入时重新读取这份文件，因此保存后无需重启管理器；已经运行的容器不会被自动缩容、停止或重启。安全线可设为 10%–99%，固定预留可设为 0–256 GiB。配置损坏或无法读取时，新启动会安全失败，现有容器保持不变。

遥测、估算或租约状态不可用时，启动会安全失败。新增模式不会改变现有容器；替换模式会自动恢复刚才的回滚点。加载期间租约每分钟续期，管理器异常退出后的 pending 租约最迟约 15 分钟回收；成功后只保留短冷却，失败或取消会立即释放。锁目录用进程存活检查、旧锁令牌回收权和原子改名共同保护，不能把慢准入或刚获得锁的后继误判成死锁。

准入通过后，Docker 的 `--gpus` 会强制绑定到租约实际批准的宿主 GPU。即使表单没有显式填写 GPU，也不会再因为空参数被 Docker 解释为“使用全部 GPU”。并行实例的默认显存利用率为 70%；vLLM 以配置比例做保守预留，llama.cpp 会解析本地 GGUF 元数据，并加入上下文、并发、组件和运行时开销下限。同一目录中的 `dynamic`、`17gb` 等主 GGUF 会作为替代变体分别展示和估算，不会把多个完整模型相加；启动前必须确定一个具体主变体。`mmproj` 视觉投影和 DFlash 推测解码模型属于可选组件，只在启用或匹配时追加到选中主变体的预算。仍无法确定主 GGUF 的远程模型或目录会返回 422，而不是接受用户随意填低的比例。

普通 GGUF 使用已验证的 llama.cpp `b10630` CUDA 镜像，前端可配置 reasoning effort、reasoning budget 与 mmproj device；实验性的 tools runtime 不在网页端开放。历史 Muse 镜像和兼容代码仅为回滚保留，本轮不下载、不验证，也不把 Muse 作为受支持目标。vLLM 默认固定到 Linux/amd64 v0.28.0 的精确平台 digest `sha256:2286e8533ca8b6bc777594bae30524f1426ba46ca21797524e06df6a94b06635`，前端可配置 `max_num_batched_tokens`；本地策略会在容器创建前阻断 Muse。固定镜像没有 v0.28 外置的 `vllm-bnb-plugin`，因此 BNB checkpoint 也会被明确阻断，普通 safetensors 不受影响。

在加载新模型前仍应在对应管理器查看启动预估。建议给 KV cache、视觉编码器峰值、并发请求和驱动波动留下余量；如果需要完全确定的路由，请在客户端使用实际模型名。

## 统一入口的并发与密钥边界

- 网关单请求默认最多接收 32 MiB，硬上限 64 MiB；并发预算默认 128 MiB，并以 4 倍系数计入流分片、合并 Buffer、字符串和 JSON 对象的瞬时副本。gzip、deflate 和 br 请求会在受限预算内解码，泛型模型改写后会同步去掉旧压缩头。解析后日志只保留模型名、stream 标记和工具数量，不持有提示词正文。
- 入口签名令牌以发布文件为准、环境变量只作首次启动兜底，因此入口单独重启和轮换令牌时，两个长驻管理器无需重启。
- 新启动容器的运行时 API Key 不再额外写入 Docker label；label 只保存随机引用，管理器恢复连接所需的明文保存在各管理器的 `logs/runtime-api-keys.json`。该文件采用原子写入，并在 Windows 上移除继承权限，只授予当前账户和 SYSTEM；文件损坏、丢失引用或权限异常时会明确返回 503，而不是静默退回空密钥。普通管理器设置备份不会导出这份密钥库，升级或整目录迁移时必须连同运行数据一起保留。旧容器的历史 label 仍可读取以保持升级兼容，但所有管理 API 会统一脱敏。
- 两个管理后台即使监听局域网地址，默认也只允许本机读取和管理；远端只可访问经过 API Key 保护的模型网关。运行时仍要求把 Key 作为启动参数交给 Docker，因此拥有 Docker 管理权限的人仍属于可信边界。

## 当前边界

- 统一入口不会自动下载、启动、停止或抢占模型，避免误伤正在服务的实例。
- 能力标签来自管理器元数据和模型名启发式判断；自定义模型名可能需要使用精确模型名。
- vLLM 的权重和 KV Cache 最终分配仍由运行时决定，准入是“拒绝明显超卖”的保护线，不是 CUDA 级硬隔离；视觉编码器和首次编译仍需预留峰值空间。
- 下一阶段适合加入“一键工作集”（聊天 + 视觉 + Embedding）、准入预演、实例排空/热替换、按 TTFT/吞吐/队列长度的反馈调度，以及空闲模型的可撤销 LRU 建议。自动卸载应保持为明确的用户策略，默认不抢占现有模型。

## 推荐工作流

1. 在 vLLM 或 llama.cpp 管理器以并行实例模式启动语言、视觉、Embedding 或 Rerank 模型。
2. 回到 `http://127.0.0.1:5176/`，确认舰队实例表和显存余量。
3. 用路由预演确认所需能力已经驻留。
4. 客户端连接统一入口；需要确定性时使用精确模型名，需要能力自动选择时使用泛型模型名。
